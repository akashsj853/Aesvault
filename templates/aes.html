1. Symmetric Cryptography

In symmetric encryption, a single shared secret key is used for both the encryption of plaintext and the decryption of ciphertext.

Plaintext + Secret Key ==> Ciphertext (Encryption)
Ciphertext + Secret Key ==> Plaintext (Decryption)

Because both parties require the same key, keeping the key confidential is paramount. If an adversary acquires the key, they can decrypt all intercepted traffic.

📏

2. Key Sizes: AES-128 vs 192 vs 256

AES was standardized by NIST in 2001 (FIPS 197) to replace DES. AES supports three standardized key lengths with different internal transformation rounds:

Variant Key Size Rounds Possible Keys
AES-128 16 bytes (128 bits) 10 rounds 3.4 × 1038
AES-192 24 bytes (192 bits) 12 rounds 6.2 × 1057
AES-256 (This Project) 32 bytes (256 bits) 14 rounds 1.1 × 1077

AES-256 provides the highest level of security, rendering brute-force attacks physically impossible with classical computers.

🛡️

3. Authenticated Encryption with GCM

Traditional modes of operation like CBC (Cipher Block Chaining) or ECB (Electronic Codebook) only provide confidentiality, leaving files vulnerable to bit-flipping attacks and padding oracle exploits.

GCM (Galois/Counter Mode) provides Authenticated Encryption with Associated Data (AEAD):

  • Counter Mode (CTR): Transforms the block cipher into a high-speed stream cipher by encrypting sequential counter blocks.
  • Galois Message Authentication Code (GMAC): Uses universal hashing over the binary Galois Field GF(2128) to compute a 128-bit authentication tag.
  • Integrity Guarantee: If even a single bit in the ciphertext is altered in transit or on disk, the tag check fails automatically and decryption is refused.
🎲

4. The Role of the Nonce (IV)

A Nonce ("Number used ONCE") is a unique vector supplied alongside the key during encryption.

⚠️ CRITICAL CRYPTOGRAPHIC RULE: Nonce Reuse

In AES-GCM, NEVER reuse a nonce with the same key. Nonce reuse completely destroys the integrity guarantees of GCM and can expose the internal authentication hash key (H), allowing attackers to forge tags.

In AESVault, an independent, cryptographically secure 12-byte (96-bit) nonce is generated via os.urandom(12) for every single file encryption.

Q1: Why did you choose AES-256 over RSA or Blowfish?

Answer: RSA is an asymmetric cipher designed for key exchange and digital signatures, not for bulk file encryption—it is computationally slow and limited to encrypting data smaller than its key size. AES is a symmetric block cipher standardized by NIST, optimized for high throughput, and is the global benchmark for data-at-rest protection. AES-256 was selected because its 256-bit key offers 2256 keyspace, making brute-force attacks computationally infeasible.

Q2: What is the difference between AES-CBC and AES-GCM?

Answer: AES-CBC (Cipher Block Chaining) requires padding (PKCS#7) to fit 16-byte block boundaries and only provides confidentiality. It requires a separate MAC (like HMAC-SHA256) to detect tampering. AES-GCM (Galois/Counter Mode) does not require padding, can run in parallel for high speed, and natively produces a 128-bit authentication tag (AEAD). This ensures tamper-detection is built directly into the decryption step.

Q3: Where is the AES key stored?

Answer: For security best practices, the AES key is never stored on the server or in the database. The key is generated and provided to the user. The user is responsible for retaining the key. When decrypting, the user must supply the key. If we stored the keys in the database next to the files, any database breach would compromise all user files.

Q4: What happens if an attacker modifies one byte in the encrypted file?

Answer: During decryption, the GCM algorithm recomputes the Galois field authentication tag over the received ciphertext. If even one byte or bit has been altered, the computed tag will not match the 16-byte tag stored in the package. The Python cryptography library will throw an InvalidTag exception, and AESVault immediately rejects the file without releasing any corrupted plaintext.

Q5: Why is the nonce 12 bytes and not secret?

Answer: NIST SP 800-38D specifies a 96-bit (12-byte) nonce as the optimal size for GCM to avoid internal counter computation overhead. The nonce does not need to be secret, but it must be unique for every encryption performed with the same key. That is why it is safely stored in plaintext at the beginning of the .enc binary package.
